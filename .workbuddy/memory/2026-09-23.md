## MiniMax 端点逆向成功（提交 d78f245）

用户质疑「模拟点击被 isTrusted 过滤」的结论 —— **质疑成立**。

### isTrusted 结论修正（重要）
- `scripts/ui_claim.ps1` 用 UIA `InvokePattern.Invoke()` → 脚本层派发 → `isTrusted:false` → **会被过滤，成立**
- `ui_claim_minimax.ps1` / `ui_claim_autoclaw.ps1` 用 `SetCursorPos` + `mouse_event` → OS 级输入注入 → **isTrusted:true，不受影响**
- MiniMax 失败的真正原因是脚本 bug：
  1. 点的是「今天」标签（y≈1629），真正按钮是「签到得@400」（y≈1882）
  2. 校验窗口是「标题锚点 y≈1509 ±200」= 1309~1709，**按钮 1882 根本不在窗口内**
  → 已修：点击目标改为匹配 `签到得|领取|领积分|签到领`，校验窗口基准改为按钮位置 ±300

### 端点（从 app.asar 逆向，527MB Electron 归档）
- `GET  https://agent.minimax.cn/minimax-cloud/api/v1/signin/status`
- `POST https://agent.minimax.cn/minimax-cloud/api/v1/signin/claim`
- 鉴权：`Authorization: Bearer`（不进查询串）、`user_id` 查询参数、仅 HTTPS
- **阻塞点**：渲染进程走 `app://cloud` 自定义协议，鉴权头由**主进程**注入，
  且只放行 `/minimax-cloud/api` 前缀 → 外部 CLI 直连需自备 token
- 数据模型 `@mavis/shared/src/daily-signin.ts`：
  `SigninDayStatus 1=Upcoming 2=Claimable 3=Claimed 4=Disabled`、
  `SigninClaimResult 1=Claimed 2=AlreadyClaimed`、`day_no ∈ 1..7`

### app.asar 归档格式（可复用）
`u32@0=4`；`u32@12=json_len`；JSON 头从 offset 16 起；body 起始 = `(16+json_len)` 上对齐 4 字节。
（第一次按 `u32@4` 读 pickle_size 会失败。）

### 流程教训
**让各家 Agent「自述」这条路对 Electron 应用价值有限** —— MiniMax 答 `claim_mode: never`、
`api: unknown`，实际端点就在它自己安装目录的 app.asar 里明文躺着。它不认识自己的打包产物。
以后对 Electron 系产品（MiniMax / TraeWork / LobsterAI / AutoClaw）应直接扫本机安装目录，
自述只作为补充。

## A+B：焦点还原 + 自启动才退出（提交 729f3f7）

用户偏好：**客户端不想常开**，同一时间只用一两个。所以签到完要关掉自己启动的那个。

### 实现
- **A 焦点还原**：`Save-Foreground` 在 `Wait-Foreground` 开头记录当前前台句柄（若已是 MiniMax 则不记），
  所有退出路径在 `Out-Json` 里统一 `Restore-Foreground`
- **B 自启动才退出**：启动前快照 `Get-Process 'MiniMax Code'` 的 PID 集合，
  **`$script:CloseAllowed = (原有进程数 -eq 0)`** —— 只要原本有任何一个实例在跑，就绝不关。
  关闭走 `CloseMainWindow()` 优雅退出，8s 后残留才 `Stop-Process -Force`。默认开，`-NoClose` 退出。
- 失败（pending/notfound）时**保留客户端**并还原焦点，方便人工处理

### 发现的新阻塞：冷启动失败（比 A/B 更根本）
脚本的冷启动路径**从未真正验证过**（之前成功那次客户端本来就在跑）。
实测：从自动化上下文 `Start-Process` 启动 MiniMax Code → 进程立即消失，
`Roaming\MiniMax\logs` mtime 停在 07:23:25 未更新（即应用根本没执行到写日志），
同一上下文启动 notepad 却正常（pid 有、窗口句柄有）。
`cmd /c start` 和 `[Diagnostics.Process]::Start` 都被安全策略拦。

**影响**：冷启动不通 → B 永远不触发（只关自己启动的）→ 早上计划任务若客户端没开就直接漏签。
这是"不想常开"这个偏好的死穴：**要么客户端常开（脚本直接签不关），要么冷启动可靠（签完关）**。

### 环境坑（复用）
- 从 PowerShell 工具启动 GUI 后，`$proc.MainWindowHandle` 取不到；`.Refresh()` **不刷新**它
  （.NET 已知行为），要重新 `(Get-Process -Id $id).MainWindowHandle`
- `cmd.exe` 和 `[Diagnostics.Process]::Start` 都被本环境安全策略拦截，只能用 `Start-Process`

## 三个会误操作的定位缺陷（提交 d82ca9f）—— 比 A/B 更重要

用户确认**双击能正常开** → 应用没问题，是本会话的自动化上下文起不来 GUI。
于是趁客户端开着做验证，结果挖出三个真 bug（都会导致"看起来在跑、实际乱点"）：

### 1. Find-AppWindow 用 IsWindowVisible 过滤 → 主窗口被整个漏掉
诊断：主窗口 `h=2038348 title=[MiniMax Code] rect=260,66,1660,966 (1400x900)`，
**`IsWindowVisible=False`、`IsIconic=False`、非 topmost**。
即：在另一个虚拟桌面 → **DWM cloak** → 有正常 rect 但不可见。
去掉可见性过滤，改用尺寸判据（只有真窗口是 1400x900 量级）。

### 2. 锚点「每日签到」命中聊天区
本项目自己的会话内容里就有「每日签到」四个字 → 锚点算到了聊天列，
点击点 **2180,1483**（窗口才 1400 宽），真的点进了聊天区。
改：取**最左**命中 + 拒绝 `x > 40% 窗宽` 的候选；按钮匹配限制在 `anchor.x + 400` 内。

### 3. 最关键：OCR 结果不校验是不是 MiniMax（已加门）
MiniMax 被 cloak 时 `CopyFromScreen` 截到的是**当前桌面的 WorkBuddy**，
画面"看起来完全正常"（有文字、有布局），脚本会照着陌生窗口的坐标点击 —— 非常危险。
门：OCR 后要求顶部 80px 内有 `minimax` 字样（标题栏），否则放弃点击并报 pending。
实测生效：`截图未确认是 MiniMax 窗口（顶部无标题，可能被遮挡），已放弃点击`。
